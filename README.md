# Практическая работа № 6. Синхронизация (вариант B)

## Окружение
- Python 3.14.4
- Число ядер (nproc): 12
- WSL2, VS Code
- Запуск любого скрипта: `python3 имя_файла.py`. Файл `common.py` нужен остальным.

## Файлы
| Файл | Назначение |

| `race_counter.py` | программа с гонкой |

## 1. Состояние гонки
Файлы: `race_counter.py` (с гонкой) и `race_counter_fixed.py` (исправленная версия).
4 потока по 10 000 раз увеличивают общий счётчик, ожидаемый результат 40 000.

Вывод программы с гонкой:
```
ожидалось: 40000
получено:  10002
потеряно обновлений: 29998
время: 1.06 с
РЕЗУЛЬТАТ: ГОНКА ОБНАРУЖЕНА
```

Вывод исправленной версии:
```
ожидалось: 40000
получено:  40000
потеряно обновлений: 0
время: 5.82 с
РЕЗУЛЬТАТ: OK
```

**Объяснение.** Операция «счётчик + 1» состоит из трёх шагов: прочитать, прибавить, записать.
Если поток вытеснен между чтением и записью, обновление другого потока затирается, и оно
теряется (здесь потеряно 29 998 из 40 000). Для воспроизводимости между чтением и записью
добавлен `time.sleep(0)`: в современном Python из-за GIL простое `counter += 1`
ломается редко. В исправленной версии тело цикла то же самое, добавлен только `with lock:`,
поэтому читать, изменять и записывать счётчик может только один поток за раз.
Цена исправления: версия с мьютексом работала дольше (5.82 с против 1.06 с), потому что
потоки теперь выполняют критическую секцию по очереди, а `sleep(0)` оставлен внутри неё
специально, чтобы показать, что тот же код становится безопасным.

## 2. Производитель-потребитель (кольцевой буфер на 5 элементов)
3 производителя, 2 потребителя, 1000 элементов, `queue.Queue` не используется.
Каждый элемент имеет уникальный номер `(номер производителя, номер элемента)`.
Остановка: после завершения всех производителей в буфер кладутся два маркера STOP
(по одному на потребителя).

### 2а. Два семафора и мьютекс (`prodcons_sem.py`)
Семафор `empty` считает свободные места, `full` считает занятые, мьютекс защищает
индексы и счётчик буфера. Семафоры захватываются до мьютекса, иначе возможна
взаимная блокировка (поток заснул бы на семафоре, удерживая мьютекс).

```

буфер: 5, производителей: 3, потребителей: 2, элементов: 1000

  [OK] произведено 1000 из 1000
  [OK] потреблено 1000 из 1000
  [OK] элементов, потреблённых больше одного раза: 0
  [OK] элементов потеряно (не потреблено): 0
  [OK] посторонних элементов: 0
  [OK] нарушений инварианта буфера (0 <= count <= 5): 0
  [OK] максимальное заполнение буфера: 5 (лимит 5)
  [OK] буфер в конце пуст (count=0)
  по потребителям: C0=500, C1=500
  время: 0.27 с
ИТОГ: ВСЁ КОРРЕКТНО
```

### 2б. Мьютекс и условные переменные (`prodcons_cond.py`)
Две условные переменные `not_full` и `not_empty` на одном мьютексе.
Ожидание всегда в цикле `while`. После `put` будится один потребитель (`not_empty.notify()`),
после `get` один производитель (`not_full.notify()`).

```

буфер: 5, производителей: 3, потребителей: 2, элементов: 1000

  [OK] произведено 1000 из 1000
  [OK] потреблено 1000 из 1000

  [OK] элементов потеряно (не потреблено): 0
  [OK] посторонних элементов: 0
  [OK] нарушений инварианта буфера (0 <= count <= 5): 0
  [OK] максимальное заполнение буфера: 5 (лимит 5)
  [OK] буфер в конце пуст (count=0)
  по потребителям: C0=501, C1=499
  время: 0.20 с
ИТОГ: ВСЁ КОРРЕКТНО
```

### Проверка корректности
Корректность подтверждена проверкой инвариантов в коде (`common.py`), а не «на глаз»:
- `RingBuffer.put` и `RingBuffer.get` проверяют инвариант 0 <= count <= 5 и логируют
  нарушения (переполнение, чтение из пустого буфера);
- после работы `verify` проверяет, что каждый из 1000 элементов потреблён ровно один раз
  (нет дубликатов и потерь), посторонних элементов нет, максимальное заполнение буфера
  не превышает 5, буфер в конце пуст и потоки завершились (нет взаимной блокировки).
В записанных запусках обе версии прошли все проверки. Оба потребителя получили примерно
по половине элементов, значит, они работали параллельно.
«Производство» и «обработка» элемента выполняются вне критической секции, чтобы она
оставалась узкой.

## 3. Барьер на условной переменной (`barrier.py`)
4 потока выполняют задачу в три фазы. Барьер многоразовый: счётчик `generation` отличает
круги, поэтому один и тот же объект работает три раза подряд. Последний пришедший поток
увеличивает `generation` и вызывает `notify_all()`, остальные ждут в цикле
`while gen == self.generation`.
Инвариант в коде: поток может начать фазу k+1 только если все 4 потока закончили фазу k.

## 4. Потерянное пробуждение (`prodcons_cond_if.py`)
Файл отличается от `prodcons_cond.py` только заменой `while` на `if` вокруг `wait()`
(в `put` и в `get`).

Вывод (в лог попадают первые 10 нарушений, все они переполнения буфера):
```
ERROR [P2] ПЕРЕПОЛНЕНИЕ буфера: put((2, 1)) при count=5
ERROR [P1] ПЕРЕПОЛНЕНИЕ буфера: put((1, 6)) при count=5
ERROR [P0] ПЕРЕПОЛНЕНИЕ буфера: put((0, 8)) при count=5
ERROR [P2] ПЕРЕПОЛНЕНИЕ буфера: put((2, 11)) при count=5
ERROR [P1] ПЕРЕПОЛНЕНИЕ буфера: put((1, 19)) при count=5
ERROR [P0] ПЕРЕПОЛНЕНИЕ буфера: put((0, 21)) при count=5
ERROR [P1] ПЕРЕПОЛНЕНИЕ буфера: put((1, 25)) при count=5
ERROR [P2] ПЕРЕПОЛНЕНИЕ буфера: put((2, 33)) при count=5
ERROR [P1] ПЕРЕПОЛНЕНИЕ буфера: put((1, 31)) при count=5
ERROR [P0] ПЕРЕПОЛНЕНИЕ буфера: put((0, 34)) при count=5
=== Условные переменные: if вместо while (НЕВЕРНО) ===
буфер: 5, производителей: 3, потребителей: 2, элементов: 1000
  [OK] потоки завершились (нет взаимной блокировки)
  [OK] произведено 1000 из 1000
  [FAIL] потреблено 916 из 1000
  [OK] элементов, потреблённых больше одного раза: 0
  [FAIL] элементов потеряно (не потреблено): 84
  [OK] посторонних элементов: 0
  [FAIL] нарушений инварианта буфера (0 <= count <= 5): 85
  [OK] максимальное заполнение буфера: 5 (лимит 5)
  [OK] буфер в конце пуст (count=0)
  по потребителям: C0=465, C1=451
  время: 0.22 с
ИТОГ: ЕСТЬ НАРУШЕНИЯ
```
Из 1000 элементов 84 потеряно, зафиксировано 85 нарушений инварианта буфера.
Версия с `while` на том же коде нарушений не даёт (см. п. 2б).

**При каком чередовании это ломается.**
1. Буфер полон (`count=5`), производитель P0 вызвал `not_full.wait()` и спит.
2. Потребитель C0 забирает элемент (`count=4`) и вызывает `not_full.notify()`. P0 разбужен,
   но чтобы выйти из `wait()`, ему нужно снова захватить мьютекс, который пока у C0.
3. C0 отпускает мьютекс. Раньше P0 мьютекс захватывает другой производитель P1 (он не спал,
   а только что закончил «производство» элемента), видит `count=4 < 5` и кладёт элемент:
   буфер снова полон (`count=5`).
4. P0 получает мьютекс и выходит из `wait()`. В версии с `if` он не проверяет условие
   повторно и вызывает `put()` при `count=5`: переполнение, элемент теряется.
   В версии с `while` P0 проверил бы условие снова, увидел `count=5` и уснул бы опять.

Симметричный случай для потребителей: разбуженный потребитель обнаруживает пустой буфер,
потому что элемент уже забрал другой потребитель, и `get()` читает из пустого буфера.

**Про терминологию.** Здесь сигнал не пропал, а был «украден»: к моменту, когда разбуженный
поток получил мьютекс, условие, о котором его уведомили, уже перестало быть верным.
Классическое «потерянное пробуждение» (сигнал посылается, когда никто ещё не ждёт, и
пропадает) предотвращается проверкой условия под мьютексом. В обоих случаях защита одна:
проверять условие в цикле `while`. Дополнительная причина для `while`: условные переменные
допускают ложные пробуждения, когда поток просыпается без всякого `notify`.

## Выводы
- Общие данные без защиты приводят к гонке (потеряно 29 998 из 40 000 обновлений). Решение:
  мьютекс и конструкция `with`, чтобы блокировка освобождалась даже при исключении.
- Критическая секция должна быть узкой: внутри только работа с общими данными, а
  «производство» и «обработка» элементов вне её, иначе потоки выполняются по очереди.
- Семафоры удобны для подсчёта ресурсов (свободные места, готовые элементы), условные
  переменные подходят для произвольных условий. Порядок важен: семафоры захватываются до
  мьютекса.
- Ожидание на условной переменной всегда в цикле `while`: с `if` потеряно 84 из 1000
  элементов.
- Барьер на условной переменной должен различать круги (`generation`), иначе его нельзя
  использовать повторно.
- Корректность многопоточной программы подтверждается инвариантами в коде и
  контрольными запусками (барьер без барьера, `if` вместо `while`), которые показывают,
  что проверка действительно ловит ошибки.
